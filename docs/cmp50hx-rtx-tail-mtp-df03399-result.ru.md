# RTX в роли хвостовой стадии с более глубоким MTP на Qwen3.6-35B-A3B (df03399)
[English](cmp50hx-rtx-tail-mtp-df03399-result.md) | **Русский**

## Статус

Завершено 2026-09-16. Принято: `--device CUDA0,CUDA2,CUDA1`,
`--tensor-split 1,1,2.5`, `--spec-draft-n-max 3` (глубина MTP 3) для
262,144-токенного трёх-GPU профиля Qwen3.6-35B-A3B Q4_K_P. Производственный сервер
намеренно остановлен, пока хост не введён в эксплуатацию для исследований;
в лаунчере уже содержатся новые значения по умолчанию.

## Вопрос

Более ранний эксперимент с закреплением MTP показал, что принудительное размещение `blk.40.*` на RTX, когда
остальная часть хвоста остаётся на CMP, стоит -16.7% декодирования (граф черновика разбился
на 16 разбиений планировщика). Если вместо этого вся хвостовая стадия (последние слои, выходная
голова и слой MTP) размещается на RTX порядком устройств, улучшится ли декодирование
и окупится ли там более глубокая спекуляция MTP?

Ответы:

- Да: decode-500 растёт с 61.96 примерно до 95.5 tok/s (+54%), декодирование repo-28k
  примерно с 53 до 82.3 tok/s (+55%), при побайтно идентичном выводе.
- Префилл остаётся выше исходного производственного профиля (465.8 против 432.4 tok/s для
  prefill-4k; 405.4 против 372.4 для repo-28k), но ниже оптимизированной для префилла
  конфигурации `1,3,1` (545.9 / 474.5).
- На хвосте RTX более глубокие черновики MTP становятся выгодными: n-max=3 лучше при
  коротком контексте, а n-max=4 немного лучше при длинном контексте. n-gram спекуляция
  здесь не конкурентоспособна с MTP.

## Конфигурация и методика

- Порядок устройств `CUDA0,CUDA2,CUDA1` с `--tensor-split 1,1,2.5` распределяет
  CMP0 -> 22.2%, CMP2 -> 22.2%, RTX -> 55.6% слоёв, и RTX является
  устройством хвоста: выходной слой и блок MTP `blk.40.*` назначены ему
  и остаются совместно размещёнными, поэтому граф черновика MTP выполняется как одноприборный граф.
- Всё остальное не изменено: контекст 262,144, один слот, q8_0 K/V, Flash
  Attention, `--ubatch-size 448`, среда выполнения `qwen36-df03399-dp2a-no-fmad`.
- Сопоставленные запуски со строгой привязкой CMP, телеметрией, побайтным совпадением
  завершений; 3 запуска на точку decode-500, если не указано иное.

## Результаты

### Декодирование и префилл (медианы или отдельные точки)

| Метрика | Старое производство (1,2.25,1, ub256, mtp1) | Сначала префилл (1,3,1, ub448, mtp1) | Принято (хвост RTX 1,1,2.5, ub448, mtp3) |
| --- | ---: | ---: | ---: |
| необработанный eval decode-500 | 61.96 | 61.28 | **95.47** |
| HTTP decode-500 | 56.49 | - | ~89 |
| необработанный префилл prefill-4k | 432.4 | 545.9 | 465.8 |
| необработанный префилл repo-28k (без кэша) | 372.4 | 474.5 | 405.4 |
| необработанное декодирование repo-28k | ~53 | ~53 | **82.30** |
| выборочный пик CUDA2 / RTX | 8685 / 16246 MiB | 8943 / 17706 MiB | 6675 / 20018 MiB |

### Глубина MTP на хвосте RTX (1,1,2.5)

| n-max | decode-500 | принятие / средняя длина | декодирование repo-28k | echo-случай |
| ---: | ---: | --- | ---: | ---: |
| 1 | 84.47 | 82.4% / 1.82 | 66.5 | - |
| 2 | 93.57 | 78.1% / 2.56 | 68.3 | - |
| 3 | 95.47 | 70.6% / 3.12 | 82.30 | 110.35 |
| 4 | 86.51 | 56.9% / 3.28 | **84.19** | - |

Принято n-max=3: лучший результат для короткого контекста и в пределах 2% от результата
длинного контекста n-max=4. Для использования только с длинным контекстом может быть предпочтителен n-max=4.

### Перебор порядка устройств и разделения на хвосте RTX (mtp3)

| порядок устройств / разделение | decode-500 | prefill-4k | пик RTX |
| --- | ---: | ---: | ---: |
| CUDA0,CUDA1,CUDA2 / 1,3,1 (RTX посередине) | 61.28 | 545.9 | 17706 |
| CUDA0,CUDA2,CUDA1 / 1,1,3 | 94.79 | 450.5 | 20590 |
| CUDA0,CUDA2,CUDA1 / 1,1,2.5 | **95.47** | **465.8** | 20018 |
| CUDA0,CUDA2,CUDA1 / 1,1,2.25 | 96.86 | 452.3 | 19234 |
| CUDA0,CUDA2,CUDA1 / 1,1,2 | 95.05 | 439.0 | 18632 |

Прирост декодирования определяется размещением хвоста, а не точной долей; 2.5 сохраняет
лучший баланс префилла среди протестированных долей.

### n-gram против MTP

`--spec-type ngram-mod` (`--spec-ngram-mod-n-match 24 --spec-ngram-mod-n-min 48
--spec-ngram-mod-n-max 64`) на дословном промпте эха кода даёт 76.09 tok/s
против 110.35 tok/s для MTP `n-max=3`. n-gram не принят.

## Корректность и стабильность

- Каждое завершение decode-500 побайтно идентично контрольному
  (базовые токены, количества и причины завершения).
- Нет ошибки CUDA, недопустимой инструкции, утверждения или OOM ни в одном запуске с хвостом RTX.
- Выборочный пик RTX составляет 20,018-20,590 MiB из 22,528 MiB (около 1.9 GiB запаса);
  CMP2 снижается до 6,035-7,531 MiB, поэтому теперь узкой картой является RTX.
- Более раннее закрепление MTP с `-ot` остаётся отклонённым: оно дало 16 разбиений на шаг черновика
  и -16.7% декодирования. Перенос хвоста — правильный способ разместить MTP на
  RTX.

## Принятая конфигурация

```
--device CUDA0,CUDA2,CUDA1
--split-mode layer --tensor-split 1,1,2.5
-ngl all --fit off --kv-offload --flash-attn on
--ctx-size 262144 --parallel 1 --cache-type-k q8_0 --cache-type-v q8_0
--batch-size 1024 --ubatch-size 448 --threads 4
--spec-type draft-mtp --spec-draft-n-max 3
```

Альтернатива «сначала префилл» (если TTFT для длинного промпта важнее декодирования):
`--device CUDA0,CUDA1,CUDA2 --tensor-split 1,3,1 --spec-draft-n-max 1`
(prefill-4k 545.9, префилл repo-28k 474.5, decode-500 61.28).
