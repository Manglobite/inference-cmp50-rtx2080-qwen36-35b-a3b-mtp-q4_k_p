# Разделение слоёв, ubatch и размещение MTP на Qwen3.6-35B-A3B (df03399)
[English](cmp50hx-split-ubatch-mtp-df03399-result.md) | **Русский**

## Статус

Завершено 2026-09-16. Принято: `--tensor-split 1,3,1` и
`--ubatch-size 448` для 262,144-токенного трёх-GPU профиля Qwen3.6-35B-A3B Q4_K_P.
Производственный сервер намеренно остановлен, пока владелец не вводит хост в
эксплуатацию для исследований; в лаунчере уже содержатся новые
значения по умолчанию.

## Вопросы

1. Можно ли принудительно разместить нативную голову MTP на RTX 2080 Ti, чтобы она не загружала
   карты CMP?
2. Освобождает ли смещение слоёв в сторону RTX VRAM карт CMP и позволяет ли использовать больший
   `--ubatch-size` при критическом контексте 262,144?
3. Действительно ли больший ubatch улучшает префилл и какова его цена при
   декодировании?

## Ответы

1. Это можно принудительно задать с помощью `-ot 'blk\.40\..*=CUDA1'`, но это явная
   регрессия: декодирование -16.7% при побайтно идентичном выводе и неизменном принятии
   черновика. Механизмом являются 15 дополнительных разбиений планировщика на шаг черновика.
2. Да: `1,3,1` высвобождает около 1 GB на картах CMP и позволяет разместить `--ubatch-size 512`;
   `1:2.5:1` и `1:2.25:1` соответствуют одному и тому же дискретному распределению слоёв, а
   `1:2.75:1` равно `1:3,1`.
3. Да, только для префилла: на `1,3,1` prefill-4k растёт с 456.0 (ub256) до
   545.9 tok/s (ub448); repo-28k (26,319 токенов) — с 386.9 до 474.5 tok/s.
   Decode-500 изменяется примерно на -1.1%; все завершения побайтно идентичны.

## Размещение MTP: что гарантировано, а что нет

- Голова MTP этого GGUF — это полный слой MoE `blk.40.*` (20 тензоров,
  `n_layer = 40`, `n_layer_all = 41`) плюс отдельный контекст, созданный на той же
  модели; второй модели для размещения нет.
- `--spec-draft-device` (и его псевдонимы) разбирается, но не используется
  `llama-server` в `df03399`; его использует только `examples/speculative`
  (`common/arg.cpp:4204`, `examples/speculative/speculative.cpp:89`). Он не
  ограничивает MTP. Более ранние производственные запуски, передававшие его, не имели эффекта.
- `-ot/--override-tensor` использует `std::regex_search` для имени тензора и
  принудительно задаёт тип буфера (`llama-model-loader.cpp:1228`); при `-lv 5` он выводит
  в журнал `tensor ... buffer type overridden to ...`. Закрепление
  `blk\.40\..*=CUDA1` перемещает все 20 тензоров на RTX.
- Результат закрепления (3 парных запуска decode-500):

  | Метрика | Контроль | Закреплено на CUDA1 |
  | --- | ---: | ---: |
  | принятие черновика | 231/267 = 86.52%, средняя длина 1.87 | идентично |
  | время eval / 500 токенов | 8126 ms | 9725 ms |
  | декодирование | 61.4 tok/s | 51.3 tok/s (-16.7%) |
  | повторно использованные графы | 279 | 279 |

- Дамп планировщика (`GGML_SCHED_DEBUG=1`, случай `dp2a-smoke-16`):
  - контрольный граф черновика MTP: 2 разбиения, `CPU` + `CUDA2` (весь слой MTP и
    его входы остаются на устройстве хвоста);
  - закреплённый: 16 разбиений, `CPU` + 15 чередующихся фрагментов `CUDA2`/`CUDA1`
    (`mtp_tok_embd-40`, `norm-40`, `mtp_h_input`, `mtp_eh_proj-40`,
    `mtp_Qcur_full-40`, `leaf_*`, ...), примерно один или два узла на разбиение.
  - Целевой граф не изменён (3 GPU-разбиения в обоих случаях).
- Вывод: замедление вызвано накладными расходами конвейера (15 дополнительных разбиений с
  синхронизацией и копированиями на шаг черновика, около +6 ms на шаг), а не качеством
  черновика. MTP должна оставаться совместно размещённой с устройством хвоста. Если MTP на RTX
  когда-либо потребуется, вместе с ней должен быть перемещён весь хвост (последние слои, выходная
  голова, маски); это другой дизайн разделения и здесь он не оправдан.

## Смещение разделения

| Разделение | Распределение слоёв (пик VRAM CUDA0/1/2, MiB) | decode-500 | prefill-4k (ub256) |
| --- | --- | ---: | ---: |
| `1,2.25,1` (старое) | 6787 / 16246 / 8685 | 61.96 (n=19) | 432.4 |
| `1,2.5,1` | 6787 / 16246 / 8685 (то же распределение) | 61.65 (n=2) | 432.2 |
| `1,2.75,1` | 6739 / 17706 / 8939 | 61.10 (n=5) | 546.3 |
| `1,3,1` | 6739 / 17706 / 8939 (то же распределение) | 61.28 (n=5) | 545.9 |

Для `1,3,1` также измерено +27.4% необработанного префилла на repo-28k без кэша промпта
(372.4 -> 474.5 tok/s) и +3% необработанного декодирования внутри этого случая.

## Перебор ubatch (разделение `1,3,1`)

необработанный префилл prefill-4k tok/s (n=2, если не указано иное), и repo-28k без кэша
промпта (26,319 фактических токенов промпта, n=2):

| ubatch | prefill-4k | repo-28k | примечание |
| ---: | ---: | ---: | --- |
| 256 | 456.0 | 386.9 | |
| 320 | 530.0 | 454.8 | |
| 384 | 499.4 | 431.5 | |
| 448 | **545.9** (n=2) | **474.5** (n=2) | принято |
| 512 | 542.3 | 468.7 | помещается только на `1,3,1` |

Для сравнения, `--ubatch-size 448` на старом разделении `1,2.25,1` также помещается:
prefill-4k 517.8 (+19.7%), repo-28k 457.3 (+22.8%), decode-500 61.58
(-0.6%), но пик CUDA2 составляет 9529 MiB (около 0.7 GiB запаса) против 8943 MiB
на `1,3,1` (около 1.3 GiB запаса).

## Принятая конфигурация и цена

- `--tensor-split 1,3,1`, `--ubatch-size 448`, `--batch-size 1024`, контекст
  262,144 (без изменений), q8_0 K/V, Flash Attention, нативный MTP `n-max=1`,
  среда выполнения `qwen36-df03399-dp2a-no-fmad`.
- Ожидаемый эффект по сравнению с предыдущими производственными значениями по умолчанию:
  prefill-4k +26% (432.4 -> 545.9), repo-28k +27% (372.4 -> 474.5),
  decode-500 -1.1% (61.96 -> 61.28). Все завершения побайтно идентичны в каждом
  парном запуске этой сессии.

## Методика и безопасность

- Сопоставленные профили различаются только `--tensor-split`, `--ubatch-size`, переопределением
  MTP или тестируемым бинарником; каждый запуск сохраняет строгую привязку CMP,
  `gpu-binding.json`, `gpu-telemetry.csv`, `server.log` и `result.json`.
- Чередующиеся пары; для каждого сравнения требуется побайтное совпадение завершений;
  в принятых запусках нет ошибки CUDA, недопустимой инструкции или OOM.
- Единственная преднамеренная неудача — более ранний OOM `--ubatch-size 512` на старом
  разделении (сохранён в `benchmarks/results/20260916-083304-...`); на `1,3,1`
  ub512 успешен, но не быстрее 448.
- В тот же день была повторно подтверждена нейтральность параметров среды выполнения:
  `GGML_CUDA_GRAPH_OPT=1` -1.5%, `GGML_CUDA_P2P=1` -0.5%.
